## 设计背后的想法

苹果树版是 Grok Build 帮我做的、放在 Cloudflare 上的个人页面。之所以在这里特意强调是哪个 AI 做的，当然是有原因的：对不起大家的眼睛，页面上那棵树和那些苹果实在是……我还是觉得有点精神污染。但从辨识度和记忆点来看，它又确实达到了效果，所以就先留着了。- 让 Claude Code 给我改版了。

虽然那个蛇身还是跟断了似的，我跟 Claude Code 重复了很多次，让它把断了的身子改一改，但还是不行。不过也能看，抓大放小嘛，就不要在这种东西上去纠结美术了。

现在的苹果树和苹果都换成了比较好看的，虽然辨识度其实有点降低，但综合来看还是现在这版比较好

后来因为看到了喜欢的头像转场粒子效果 UI，我又写了第二版。可我仍然觉得，在辨识度方面，第二版远远不如苹果树：

- **第二版：** sci-fi 粒子效果确实更 modern，文案也更好——第二版文案专门找人润色过，不像第一版直接用了 AI 生成的生肉，第一版之后还得再改。它的信息传达做得不错，但辨识度很差，记忆度基本为零，整体太常规了。
- **第一版：** 苹果树虽然有点拉，但现在毕竟不是上世纪 80 年代。那时炫酷动画很稀少，而到了今天，各种特效、大场面和转场已经随处可见，大家早就 get tired of it 了。

最重要的还是让人记得吧——当然，是以不会让人反感的方式被记住。

## 关于这个网站

这是 [Clair Y. Chen](https://github.com/YeChen-coder) 的个人网站：一棵真正画出来的果树，每个苹果代表一个项目。

GitHub Pages 个人主页地址 `YeChen-coder.github.io` 会重定向到苹果树版。

## 技术栈

网站使用静态 HTML、CSS 和 JavaScript，部署在 Cloudflare Workers 免费套餐上，不需要构建步骤。

## 本地预览

```bash
python3 -m http.server 8765
# 打开 http://localhost:8765
```

## 部署到 Cloudflare

将文件夹内容上传到 `clair-chen` Worker，也可以使用 Wrangler Pages 或 Workers 直接上传。请将 `index.html`、`styles.css`、`app.js`、`snake.js` 和 `assets/` 放在一起。

# 开发日志和吐槽

我给它加了一个基于 AWS Bedrock Agent Core 的 AI chatbot 功能。我原本以为 chatbot 是一个非常 well-designed 的问题，没想到它还会搞出事来。

其实也是受现实制约，这里面牵扯的问题有点多。

首先，AI coding agent 默认送出去的材料是我 GitHub repository 里的 README。但我这堆仓库的 README 主要是用来记录真实发生的问题机制及解决方案，并不是标准框架，所以必须扩充它的上下文来源。

第二，我平时喜欢在网页版上写 README 更新，而且写的通常是中文版。所以我搞了两个定时任务：

1. 定期（两三天一次）让 Claude Code 把我中文 README 的更新翻译成默认的英文 README。
2. 把新改动的这些中文 .md 文件转成 text 发给 AWS，让它能知道我这边的实时进度，这样 chatbot 才能拿到最新数据。

这基本上是昨天晚上搞定的。昨晚弄完后我看 Claude Code 的效果挺好就去睡了，结果今天一试又出事了。

主要是 job description 的功能。它的本意是让访问者（比如招聘人员）把 job description 贴过来，然后在 AWS 后台基于我的资料做匹配，本质上是一个更高一阶的 RAG。

结果因为它是 multi-turn 的，再加上我用的是 Haiku（最便宜的模型），受限于模型能力以及 token 成本的考虑，默认的 agent 只能拿到前 1500 个字。但大家也知道，job description 里通常充斥着大量套话，如果核心要求被前面的公司前景、公司介绍或者“我们希望你是……”这类内容挡住，匹配就完全抓瞎了。

Claude Code 面对这种问题，在前面加一层 layer 不就行了吗？多简单、多容易想到的事情啊：随便加一个 prompt 改写一下（rewrite）。之前在 Jesus says Hi 的项目里 Claude Code 还主动跟我提议过这个方案，为什么在这里就完全想不到？rewrite 难道是一个很难想到的事情吗，非得等我提出来才去做？- 哎呀，我要被 Claude Code 给气死了！本来它对贴上来的 job description 进行匹配，就是一个工作流，是一个多 agent 的结果。哪怕在当前什么都没更新的情况下，它本来就有这么一步：提取里面的关键点，把拿到的关键点交给下一位 agent 去查我的资料，然后再接着正常往下走。提取关键点这一层，其实现在还能直接拿去复用。

可是当时 Claude Code 就没有想到 multi-turn conversation 怎么办。具体来说，就是访问者贴完 description，我的 AWS 后台也已经把匹配结果发过来了，但如果访问者再接着问，该怎么办？Claude Code 根本就没想过这个问题，单纯把那单一步测好，就告诉我完事了。这样造成的一个直接后果就是，对之后的访问者来说，如果再去问什么东西，发给 AWS 的其实是前文贴的那个 job description 的前 1500 个字，而不是经过一层LLM总结过后的要点。那确实得炸，这事儿确实是前言不搭后语的。改进方法也好说，就是复用嘛。你本来这一层就写完了，那就是在浏览器上把 message 从原本完整的 job description 改成这个总结嘛

等一下，这个事情又是个坑。

我之前说用 OpenAI API 的时候，是可以在 session.update 里面临时针对当前这一次问答去重新设置 instruction 的。但问题是，现在用的不是 Bedrock Converse API 嘛，它跟 OpenAI 的 Realtime API 不太一样。虽然大家底层模型其实都差不多，但机制上差别挺大的。

Bedrock 这边的要求是，只有这次请求里面带上的 message 才算数；如果没带，模型就不知道发生了什么，因为它是无状态的。

不过其实这样更好用：OpenAI 是有状态的，服务器会替你保存一整段对话，一旦加进 conversation 里面其实就不太好剔出来了；而无状态对整个 context 的控制力其实更好.

其实 Bedrock 这边才更接近我最开始对 Large Language Model 的 Context Window 的理解：它就是 System 加上 Message 嘛。

System 就是系统提示词，因为是无状态的，所以每次请求都要重新发。

Message 就是最近 6 条历史，每条截到 1500 字，再加上这次的一个新问题。这样的话，其实花活就很好整了

到这里首先确定的是，要去把 job description 的原文替换掉。

它肯定不能放在 system 里面，否则万一里面随便写点什么东西搞出 prompt injection，那不就炸了？你怎么着也不能放 system，没别的地方可放，二选一不就只能放 message 了。

分流靠的是同一个大模型（Claude Haiku 4.5）自己判断，不是关键词匹配。 每次提问时，智能体把分流规则（写在系统提示词里）、工具清单和访客的问题一起交给模型，由模型决定这次该看猫、查资料、留言、做 JD 匹配，还是直接回答。

因为现在这个模型已经有了，OpenAI 也明确说明了有这种只做选择、不输出 text 的 globally available 模型，所以就探索了一下：能不能在当前情况下，把原本用于分流的 high-cost 模型换成这种只做选择的模型

既然都谈到这儿了，就顺手给它摸一遍吧。我们现在只谈 Bedrock，反正场景就架在这儿。

Bedrock 上主要分两种分流：

1. 意图分流：判断访客想干什么，然后走对应的流程。这正是我这边所需要的，比如判断对方是看猫、查资料、留言，还是做 job description 匹配
2. 模型分流：同一个问题交给便宜的小模型还是贵的大模型回答。这个跟我们目前做的事没什么关系

Bedrock 的 Converse 接口里有一个 toolConfig / toolChoice 参数，它可以设定几种模式：
• auto：由模型自己决定调不调工具、要不要说话，这也是我现在正在用的
• any：必须调用一个工具，不能直接输出文字
• tool：必须调用指定的那个工具

所以这在技术上完全可行。如果要改成只负责选择、不输出文字的专门分流器，做法就是找一个更便宜的小模型（虽然 Haiku 已经很便宜了，但还有更便宜的，比如 Amazon Nova Micro），给它一个选择性工具，选项设为 A、B、C、D，参数设为 any，强制它只返回选择结果。

我现在突然觉得，商用跟个人用确实还是有版本差距。商用方案比像 Dify 这种个人用的工具还是要领先一个版本：工业界里分流器早就成熟了，是一个正儿八经的专有名词，都不知道用了多少年；而个人工具是这几个月才火起来，大家才开始去摸索各种各样的用法

第二种是 Bedrock Agents 的带路由主管模式（Supervisor with Routing）。这是 Bedrock 托管的多智能体功能，主管会先尝试把简单的请求直接转给对应的子智能体，判断不清楚的再走完整的编排流程。不过它属于 Bedrock Agents 那套托管产品，而我们整体是自己写循环跑在 Agent 块上的，不太合辙。如果非要整合，只能把我们现有的东西在那边重新实现一遍。这个方案我觉得还是有继续了解的价值，但先往后放，把当前的事情说完。

第三种办法是 Intelligent Prompt Routing。它是做模型分流的，在同一家族的两个模型之间（比如 Claude Haiku 和 Sonnet），根据预估难度自动选择一个来回答。我估计前两天面试的工程师跟我说的就是这个方案。我后来琢磨了大概十分钟，还在想怎么根据用户问题的难度去分流，难道是硬写一套 rule-based 规则？结果人家 AWS 老牌云厂商本来就自带 Intelligent Prompt Routing，我那种 rule-based 的土办法可以直接抛掉了。不得不说，我平时的学习速度还是太低，准确说是没在云厂商现成的方案上用功，精力全跑去造“赛博男友”了。

第四种是向量相似度分流。这种不需要大模型，也不是 rule-based，而是把访客的问题转成向量，看跟哪条线路的示例最接近。只需要一次 embedding 调用，耗时几十毫秒，基本不花钱，结果也很稳定。它的缺点则是理解不了复杂模糊的表达。至于 rule-based，确实没人用了，还是让它留在历史的尘埃里吧


我评估了一下当前我们网站要不要加独立分流器，结论是不太建议加。

原因主要有两点：

1. 架构上没必要：现在的分流和回答是在同一个 Prompt 里叮嘱一下、模型调用一次就完成了，分流本身既不额外花钱，也不额外花时间。如果单独加一个独立分流器，肯定会多一次调用；虽然延迟其实不是主要问题（走云厂商内网也就几毫秒），但依然多了一层复杂度。
2. 成本上不划算：独立分流器真正划算的场景是主模型很贵的时候（比如 Sonnet、Opus）。先用便宜的小模型分流，就能少调一些贵模型。比如用户只是想 reset password，顺着处理就完事了，用不着调 Sonnet，更犯不着调 Opus。但问题是我们现在根本就没做这种模型分流，用的本来就是最便宜的 Haiku，再怎么省也省不下几分钱。

以后如果想把它做得更好、更聪明一点，或者发现当前的 performance 确实不行、经常判错的时候，再去换吧
